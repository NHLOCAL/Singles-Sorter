# Restart acceptance: journal namespace and live WebView data

The desktop host sets its journal directory to `app.path().app_local_data_dir()` in `src-tauri/src/lib.rs`. It does not override the WebView data directory. Recursively snapshotting that entire directory can therefore reach a live browser cache and locked files during normal UI activity, rather than measuring only the inspection's journal/profile effects.

The repository pins Tauri **2.12.3**. Its exact source URLs were unavailable through the research tool and no matching local crate cache was found. The official [Tauri manager source page](https://docs.rs/crate/tauri/latest/source/src/manager/webview.rs) actually opened as **2.12.1**, and sets the default Windows WebView data directory to the app-local data directory. Search summaries labelled that page 2.12.3; that label is not treated as exact pinned-source proof. Official [Tauri filesystem documentation](https://v2.tauri.app/ja/plugin/file-system/) identifies the Windows browser-data subtree as `$APPLOCALDATA/EBWebView`. Microsoft documents that the [WebView2 user-data folder](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/user-data-folder) contains mutable browser state and cache. Actual Windows gates still must confirm the pinned application's layout and behavior.

The helper now captures the full app/journal namespace, including the root, every journal file and the complete `profile-v1` tree. Full content hashes, identity, permissions/ACLs, attributes and modified times remain strict outside one literal top-level `EBWebView` directory. Unknown files, new empty directories, nested `EBWebView` names, similarly named cache folders and locked files elsewhere are not exempted.

For that one browser-data directory only, the receipt records an explicit `live_webview_subtree` boundary with exact name, directory kind, identity, permissions/ACLs and attributes. It does not recurse into browser contents and omits only the boundary directory's mutable last-write timestamps. Links/reparse points or a file at that name are refused. Its absence is valid; appearance, removal, replacement or permission/attribute changes still alter the snapshot. The journal root itself is not exempted.

This changes test evidence collection only: no product data-directory override, cache migration, journal relocation, cleanup or altered inspection authority. The existing no-file-or-journal-writes check continues to cover media and the complete journal namespace; it makes no no-write claim about the browser's own live data. Portable regressions simulate a locked browser file, cache churn, new namespace entries, changed profile/journal data and metadata, changed boundary identity/ACL, unsafe boundary kinds and unexpected locked directories. They do not prove actual Windows WebView execution.
